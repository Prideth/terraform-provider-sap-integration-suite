# sapintegrationsuite_fault_message_type (Resource)

Manages a fault message type: the message structure that service interfaces and mappings refer to.
SAP generates the fault message type's schema itself: a root element named `name` with SAP's
standard fault data (`ExchangeFaultData`) and, as additional detail, the data type given in
`data_type_id`. You do not upload a schema.

**Status:** unofficial. Needs `enable_unofficial = true`. SAP documents no request for
fault message types: the Integration Content API's `$metadata` declares them, and the create, update,
`SaveAsVersion` and delete requests this resource sends were tested on a tenant, and its
acceptance test passed on a tenant (October 2026). Because the API is undocumented, SAP may change it
without notice.

## Prerequisites

- An integration package, usually [`sapintegrationsuite_integration_package`](integration_package.md).
- Usually a data type, [`sapintegrationsuite_data_type`](data_type.md).
- An OAuth client with `WorkspacePackagesEdit`.

## Lifecycle

| Operation | What happens |
|---|---|
| Create | Creates the fault message type without content; SAP generates the schema. With `save_as_version`, saves it under that version. |
| Read | Reads name, namespace, description and version, and the data type from SAP's generated bundle. |
| Update | A change of `description` or `data_type_id` updates the fault message type in place; SAP regenerates the schema. |
| Replacement | Changing `fault_message_type_id`, `package_id`, `name` or `namespace`, or removing `description` or `data_type_id`, creates a new fault message type. SAP refuses to update the name. |
| Delete | Deletes the fault message type. |

**The data type reference.** SAP's read returns `DataTypeUsed` empty even when it took effect, so
the provider reads the data type from the bundle SAP generated. SAP does not check references: it
lets you delete a data type that a fault message type uses. Refer to the data type resource, as in the
example, so that Terraform deletes the fault message type first.

## Example Usage

```terraform
# Fault message types are unofficial: SAP documents no request for them.
# Needs enable_unofficial = true in the provider block.
resource "sapintegrationsuite_fault_message_type" "order_rejected" {
  package_id            = sapintegrationsuite_integration_package.sales.id
  fault_message_type_id = "OrderRejected"
  name                  = "OrderRejected"
  namespace             = "urn:example:sales"
  description           = "Order could not be processed"
  data_type_id          = sapintegrationsuite_data_type.rejection_detail.data_type_id
}
```

## Schema

### Required

- `fault_message_type_id` (String) Technical ID of the fault message type. Changing it replaces the fault message type.
- `name` (String) Name of the fault message type, also the name of its root element. Changing it replaces the fault message type: SAP refuses to update the name.
- `namespace` (String) XML namespace of the fault message type. Changing it replaces the fault message type, because an in-place namespace change was not tested.
- `package_id` (String) ID of the integration package the fault message type belongs to. Changing it replaces the fault message type.

### Optional

- `data_type_id` (String) ID of the data type the fault message type is built on, usually sapintegrationsuite_data_type.<name>.data_type_id. Changes in place; removing it replaces the fault message type. SAP does not check that the data type exists or stays: it lets a data type in use be deleted.
- `description` (String) Description. Changes in place; removing it replaces the fault message type, because clearing it in place was not tested.
- `save_as_version` (String) Version to save the uploaded fault message type under, for example "1.0.3", using SAP's SaveAsVersion function import. Without it, SAP keeps its own version number and uploads update the current draft. The content is saved as a new version only when this value changes, so bump it together with the content for each release; version then reports what SAP recorded.

### Read-Only

- `id` (String) Composite identifier in the form "<package_id>/<fault_message_type_id>".
- `version` (String) The design-time version SAP reports.

## Import

```shell
terraform import sapintegrationsuite_fault_message_type.order_rejected Sales/OrderRejected
```

The ID is `<package_id>/<fault_message_type_id>`.

## Limitations

- **SAP:** no documented request; the contract comes from the `$metadata` and tenant tests.
- The schema is always generated from the data type; a fault message type with its own schema content is not
  supported.
