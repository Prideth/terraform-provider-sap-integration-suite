# sapintegrationsuite_key_pair_certificate_chain (Resource)

Gives a key pair a certificate signed by a certificate authority. SAP generates every key pair
with a self-signed certificate. Many receivers only trust client certificates that a known
authority issued, and they expect the tenant to present the whole chain of intermediate
certificates in the TLS handshake. The flow has three steps:

1. Read the certificate signing request (CSR) from
   [`sapintegrationsuite_key_pair`](key_pair.md)`.certificate_signing_request`.
2. Have it signed by your certificate authority: a PKI, a partner's CA, or for tests the
   `hashicorp/tls` provider.
3. Put the signed certificate and the certificates that issued it into `certificate_chain`.

SAP then presents the signed certificate and its chain wherever the key pair is used.

**Status:** unofficial. Needs `enable_unofficial = true`. SAP Help names importing a chain and
creating a CSR as capabilities of the Key Pair API, but the requests are documented only in the
API specification on the Business Accelerator Hub. This resource uses what the tenant `$metadata`
declares. A tenant probe verified every request, and the acceptance test signed a key pair's CSR,
uploaded, read back and imported the chain, and signed and uploaded again after the key pair was
regenerated (October 2026). Because the API is undocumented, SAP may change it without notice.

## Prerequisites

- A key pair, usually [`sapintegrationsuite_key_pair`](key_pair.md).
- An OAuth client with `SecurityMaterialEdit`.

## Lifecycle

| Operation | What happens |
|---|---|
| Create | Uploads the chain to the key pair (`PUT CertificateChainResources('<hexalias>')/$value`, confirming the fingerprint as the UI does). SAP refuses a certificate that was not issued for the key pair's public key. |
| Read | Exports the chain SAP holds (`KeystoreEntries('<hexalias>')/ChainResource/$value`). The configured text is kept while SAP holds the same certificates; any other chain, for example the self-signed certificate of a regenerated key pair, replaces it, and the next plan uploads the configured chain again. |
| Update | Uploads the changed chain; SAP replaces the one it held. |
| Replacement | Changing `key_pair_alias`. |
| Delete | Nothing is sent: SAP has no request that removes a chain. The key pair keeps the signed certificate until it is regenerated. Terraform shows a warning. |

`certificate_chain` takes PEM `CERTIFICATE` blocks in any order. The root may be left out, and a
signed certificate alone is accepted too. Any other block, above all a private key pasted by
mistake, fails the plan before anything is sent. `certificates` lists the chain leaf first, with
subject, issuer, serial number, validity and fingerprint, parsed locally.

## Example Usage

```terraform
# Needs enable_unofficial = true in the provider block: the CSR and the
# chain upload are known only from the tenant $metadata.

variable "ca_cert_pem" {
  type        = string
  description = "PEM certificate of the issuing certificate authority."
}

variable "ca_private_key_pem" {
  type      = string
  sensitive = true
}

resource "sapintegrationsuite_key_pair" "client_auth" {
  alias       = "client-auth-key"
  key_type    = "RSA"
  key_size    = 2048
  common_name = "client.example.com"
  country     = "DE"
}

# Sign the key pair's certificate signing request. The hashicorp/tls
# provider stands in for a certificate authority here; in practice the
# signed certificate usually comes from your PKI or a partner's CA.
resource "tls_locally_signed_cert" "client_auth" {
  cert_request_pem      = sapintegrationsuite_key_pair.client_auth.certificate_signing_request
  ca_cert_pem           = var.ca_cert_pem
  ca_private_key_pem    = var.ca_private_key_pem
  validity_period_hours = 8760
  allowed_uses          = ["digital_signature", "key_encipherment", "client_auth"]

  # A regenerated key pair has a new CSR. tls updates a changed
  # cert_request_pem in place without signing it again, so sign anew
  # whenever the key pair is replaced.
  lifecycle {
    replace_triggered_by = [sapintegrationsuite_key_pair.client_auth]
  }
}

# The signed certificate with the certificate of its issuer. When the key
# pair is replaced, the new CSR is signed and the chain uploaded again in
# the same apply.
resource "sapintegrationsuite_key_pair_certificate_chain" "client_auth" {
  key_pair_alias    = sapintegrationsuite_key_pair.client_auth.alias
  certificate_chain = join("", [tls_locally_signed_cert.client_auth.cert_pem, var.ca_cert_pem])
}
```

## Schema

### Required

- `certificate_chain` (String) The key pair's signed certificate and the certificates that issued it, as one PEM bundle of CERTIFICATE blocks in any order; the root may be left out. Any other block, above all a private key, is refused. Not sensitive: certificates are public. SAP refuses a certificate that was not issued for this key pair's public key. On refresh the configured text is kept as long as SAP holds the same certificates; a different chain on the tenant replaces it, leaf first.
- `key_pair_alias` (String) The alias of the key pair the chain belongs to, for example sapintegrationsuite_key_pair.example.alias. Changing it replaces the resource.

### Optional

- `runtime_location_id` (String) NOT SUPPORTED YET. Edge Integration Cell targeting has not passed its acceptance test on a tenant with an Edge Integration Cell; leave this unset until it has. If set, requests go to /location/<id>/api/v1 on the same tenant host, the service root SAP Help documents for Edge Integration Cells, and the value is the runtime location ID SAP shows in the monitoring URL after selecting the Edge Integration Cell as runtime ({"edge":{"runtimeLocationId":"myedge"}}). Use it only at your own risk. Changing it replaces the resource.

### Read-Only

- `certificate_sha256` (String) The SHA-256 fingerprint (lowercase hex) of the key pair's signed certificate, computed locally from certificate_chain.
- `certificates` (Attributes List) The certificates of the chain, parsed locally, leaf first: the key pair's certificate, then each issuer. (see [below for nested schema](#nestedatt--certificates))
- `id` (String) Always equal to key_pair_alias.

## Import

```shell
terraform import sapintegrationsuite_key_pair_certificate_chain.client_auth client-auth-key
```

The ID is the key pair's alias. The chain SAP holds is read back, leaf first; when the
configuration holds the same certificates, the first plan after the import shows no change.

## Limitations

- **SAP:** a chain cannot be removed, only replaced or dropped together with the key pair.
- **SAP:** after the upload, SAP reports the signed certificate's issuer, serial number and
  validity for the key pair. [`sapintegrationsuite_key_pair`](key_pair.md) keeps the validity
  it was generated with, so the upload does not plan a replacement of the key pair.
- **Provider:** when the key pair is regenerated, the old chain no longer fits its new key. In a
  configuration that signs `certificate_signing_request` itself, the new CSR is signed and the
  chain uploaded in the same apply, provided the signing resource is replaced with the key pair.
  `tls_locally_signed_cert` of the `hashicorp/tls` provider updates a changed
  `cert_request_pem` in place without signing again; give it
  `lifecycle { replace_triggered_by = [sapintegrationsuite_key_pair.<name>] }` as in the example.
  A chain kept as a fixed text fails with SAP's error "The public key of the CA Reply is
  different" until it is signed again.
- **Provider:** `runtime_location_id` (Edge Integration Cell) was not tested with chains.
