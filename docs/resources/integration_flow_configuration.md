# sapintegrationsuite_integration_flow_configuration (Resource)

Integration flows expose settings as externalized parameters, so the same flow can run against
different systems in development, test and production without editing its model. This resource
sets the values of the parameters you list. It is the Terraform counterpart of *Configure* in
the Integration Suite UI.

**Status:** supported. Backed by `IntegrationDesigntimeArtifacts(Id,Version)/Configurations`
and its documented `$links/Configurations` update in the Integration Content API.

## Prerequisites

- An integration flow whose model externalizes the parameters, usually from
  [`sapintegrationsuite_integration_flow`](integration_flow.md). The keys are defined in the
  flow; this resource cannot create new ones.
- An OAuth client with `WorkspacePackagesConfigure`.

## Lifecycle

| Operation | What happens |
|---|---|
| Create | Reads the parameters of `flow_version`, rejects keys the flow does not have, and writes each listed value with the parameter's existing data type. |
| Read | Reads the current values of the managed keys. A value changed in the UI shows as drift. |
| Update | Writes all listed keys again. When `flow_version` changes, for example after `save_as_version` on the flow, the values are written into the new version. |
| Replacement | Changing `flow_id` manages the parameters of another flow. |
| Delete | Stops managing the parameters and leaves their values on the flow, with a warning. SAP has no operation to reset or delete a parameter. |

Only the listed keys are managed. Every other parameter of the flow keeps its value and is
never written.

New values take effect at runtime only after a redeploy, and changing parameters does not
change the flow's version. List the parameters in `redeploy_triggers` of
[`sapintegrationsuite_integration_flow_deployment`](integration_flow_deployment.md) so that a
changed value redeploys the flow in the same apply.

## Example Usage

```terraform
# Environment-specific values for the externalized parameters of the flow.
# Only these keys are managed; any other parameter keeps its value.
resource "sapintegrationsuite_integration_flow_configuration" "metering" {
  flow_id      = sapintegrationsuite_integration_flow.metering.flow_id
  flow_version = sapintegrationsuite_integration_flow.metering.version

  parameters = {
    receiver_host       = "meter-gateway.prod.example.invalid"
    receiver_credential = "METER_GATEWAY_OAUTH"
    batch_size          = "250"
  }
}

# Parameters take effect at runtime only after a redeploy. Listing them in
# redeploy_triggers redeploys the flow in place whenever a value changes.
resource "sapintegrationsuite_integration_flow_deployment" "metering" {
  package_id   = sapintegrationsuite_integration_package.utilities.id
  flow_id      = sapintegrationsuite_integration_flow.metering.flow_id
  flow_version = sapintegrationsuite_integration_flow.metering.version

  redeploy_triggers = sapintegrationsuite_integration_flow_configuration.metering.parameters
}
```

## Schema

### Required

- `flow_id` (String) ID of the integration flow.
- `flow_version` (String) Design-time version whose parameters are set, typically sapintegrationsuite_integration_flow.<name>.version. When it changes, all managed parameters are written again into the new version.
- `parameters` (Map of String) Parameter keys and the values to set, as strings. Each key must exist as an externalized parameter of the flow version. The parameter's existing data type is kept.

### Read-Only

- `id` (String) Same as flow_id.

## Import

```shell
# "<flow_id>/<flow_version>". Import adopts every parameter the version has;
# keys you leave out of the configuration afterwards are simply no longer managed.
terraform import sapintegrationsuite_integration_flow_configuration.metering metering/1.0.3
```

The ID is `<flow_id>/<flow_version>`. An import records every parameter the flow version has.
List only the keys you want to manage; the first plan then shows the other keys leaving
`parameters`, and applying leaves their values unchanged on the tenant.

## Limitations

- **SAP:** parameters come from the flow model; there is no API to create, delete or reset
  one. Whether uploading new flow content keeps the values is not documented. If it resets
  them, the next plan shows the managed keys as drift and applying writes them again.
- **Provider:** values are strings, as SAP stores them; the parameter's data type is kept and
  not validated by the provider. Secrets do not belong in parameters: reference a credential
  alias from [`sapintegrationsuite_user_credential`](user_credential.md) or
  [`sapintegrationsuite_oauth2_client_credential`](oauth2_client_credential.md) instead.
