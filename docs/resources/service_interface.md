# sapintegrationsuite_service_interface (Resource)

Manages a service interface: the operations an interface offers and the message types they
exchange. Each operation names a request message type, a response message type if it is
synchronous, and the fault message types it can raise. An operation with a response message type
is synchronous; one without is asynchronous.

**Status:** experimental. Needs `enable_experimental = true`. SAP documents no request for service
interfaces: the Integration Content API's `$metadata` declares `ServiceInterfaceDesigntimeArtifacts`,
and the operation model this resource writes follows the bundles SAP's own editor wrote for an
asynchronous and a synchronous service interface. Tenant probes confirmed the create, the upload of
an asynchronous operation, `SaveAsVersion` and the delete. Once its acceptance test has passed on a
tenant, the resource becomes unofficial and needs `enable_unofficial = true` instead, because SAP
may change an undocumented API without notice.

## Prerequisites

- An integration package, usually [`sapintegrationsuite_integration_package`](integration_package.md).
- The message types and fault message types the operations use, usually
  [`sapintegrationsuite_message_type`](message_type.md) and
  [`sapintegrationsuite_fault_message_type`](fault_message_type.md).
- An OAuth client with `WorkspacePackagesEdit`.

## Lifecycle

| Operation | What happens |
|---|---|
| Create | Creates the service interface without content (SAP generates one operation without messages), then writes the configured operations into its bundle and uploads it. With `save_as_version`, saves it under that version. |
| Read | Reads name, namespace, description and version, and the operations from the operation model in the bundle. |
| Update | A change of `description` or of the operations rewrites the operations in the current bundle and uploads it. |
| Replacement | Changing `service_interface_id`, `package_id`, `name` or `namespace`, or removing `description`, creates a new service interface. |
| Delete | Deletes the service interface. |

**How the operations are written.** The bundle of a service interface is an archive that holds
the interface's own bundle and a resolved child, both archives themselves. The operations live in
`src/main/resources/json/<name>.json` of the interface's own bundle. For every message the
provider reads the referenced message type or fault message type and records its ID, name,
namespace, version and package, as SAP's editor does; the manifest names the referenced types in
`Require-Capability`. SAP needs the name next to the content in the upload and stores the
operations itself; it does not keep every field the editor writes (for example `messageDetails`).

**References are not checked.** SAP does not check that the message types an operation names exist
or stay. Refer to the message type resources, as in the example, so that Terraform creates them
first and deletes the service interface before them.

## Example Usage

```terraform
# Service interfaces are experimental: SAP documents no request for them.
# Needs enable_experimental = true in the provider block.
resource "sapintegrationsuite_service_interface" "orders" {
  package_id           = sapintegrationsuite_integration_package.sales.id
  service_interface_id = "OrderService"
  name                 = "OrderService"
  namespace            = "urn:example:sales"
  description          = "Order intake"

  operation = [
    {
      # Synchronous: a request, a response and a fault.
      name                     = "CreateOrder"
      request_message_type_id  = sapintegrationsuite_message_type.order.message_type_id
      response_message_type_id = sapintegrationsuite_message_type.confirmation.message_type_id
      fault_message_type_ids   = [sapintegrationsuite_fault_message_type.rejection.fault_message_type_id]
    },
    {
      # Asynchronous: a request only.
      name                    = "CancelOrder"
      request_message_type_id = sapintegrationsuite_message_type.cancellation.message_type_id
    },
  ]
}
```

## Schema

### Required

- `name` (String) Name of the service interface. Changing it replaces the service interface, because an in-place rename was not tested.
- `namespace` (String) XML namespace of the service interface. Changing it replaces the service interface, because an in-place namespace change was not tested.
- `operation` (Attributes List) The operations, in order. An operation with a response message type is synchronous, one without is asynchronous. Changes in place: the provider writes the operations into the service interface's bundle and uploads it. (see [below for nested schema](#nestedatt--operation))
- `package_id` (String) ID of the integration package the service interface belongs to. Changing it replaces the service interface.
- `service_interface_id` (String) Technical ID of the service interface. Changing it replaces the service interface.

### Optional

- `description` (String) Description. Changes in place; removing it replaces the service interface, because clearing it in place was not tested.
- `save_as_version` (String) Version to save the uploaded service interface under, for example "1.0.3", using SAP's SaveAsVersion function import. Without it, SAP keeps its own version number and uploads update the current draft. The content is saved as a new version only when this value changes, so bump it together with the content for each release; version then reports what SAP recorded.

### Read-Only

- `category` (String) Direction SAP records for the interface, OUTBOUND for an interface created through the API.
- `id` (String) Composite identifier in the form "<package_id>/<service_interface_id>".
- `interface_pattern` (String) Interface pattern SAP records, STATELESS for an interface created through the API.
- `version` (String) The design-time version SAP reports.

## Import

```shell
terraform import sapintegrationsuite_service_interface.orders Sales/OrderService
```

The ID is `<package_id>/<service_interface_id>`.

## Limitations

- **SAP:** no documented request; the contract comes from the `$metadata`, SAP's own bundles and
  tenant probes.
- A synchronous operation written through the API has not been tested on a tenant yet; its form
  follows a synchronous service interface SAP's editor created.
- The provider writes outbound, stateless interfaces (`category` and `interface_pattern` show what
  SAP records); other categories and patterns were not examined.
