# sapintegrationsuite_data_type (Resource)

Manages a data type: a complex XML type that message types and service interfaces of the same
package build on. You provide the schema; the provider uploads it as a data type artifact.

**Status:** supported. SAP's Integration Content API specification on the Business Accelerator
Hub documents `DataTypeDesigntimeArtifacts`: create, read, update, delete, the content download
and `DataTypeDesigntimeArtifactSaveAsVersion`. An acceptance test created a data type, changed its
schema and description in place, imported it and saved a version on a tenant (October 2026). The
specification describes the content only as a ZIP archive; the bundle the provider builds from
`xsd` follows the layout SAP itself stores for a data type.

## Prerequisites

- An integration package, usually [`sapintegrationsuite_integration_package`](integration_package.md).
- The schema of the data type: an `xsd:schema` with exactly one top-level `complexType`.
- An OAuth client with `WorkspacePackagesEdit`.

## Lifecycle

| Operation | What happens |
|---|---|
| Create | Builds the artifact bundle from `xsd`, `namespace` and `description` and uploads it; with `save_as_version`, saves it under that version. |
| Read | Reads name, namespace, description and version. `xsd` keeps the value of the last apply. |
| Update | A change of `xsd`, `name` or `description` uploads a new bundle with `PUT`. A changed `save_as_version` saves a new version. |
| Replacement | Changing `data_type_id`, `package_id` or `namespace` creates a new data type. |
| Delete | Deletes the data type. |

**The bundle.** SAP stores a data type as a bundle with the schema, a manifest and two attribute
files. A package export from the UI lacks the attribute files, and SAP rejects such a bundle with
`500` "map is null". The provider therefore builds the bundle itself, in the layout SAP returns
for a data type. SAP takes the description and the namespace from the request, not from the
bundle, so the provider sends them with every create and update.

**The schema.** The plan checks that `xsd` is well-formed, has `xsd:schema` as root element,
exactly one top-level `complexType`, and the `targetNamespace` given in `namespace`. SAP stores
the complex type under the data type's `name`; if your schema uses another name, the plan warns,
because references to the type must use the stored name.

## Example Usage

```terraform
resource "sapintegrationsuite_data_type" "order" {
  package_id   = sapintegrationsuite_integration_package.sales.id
  data_type_id = "Order"
  name         = "Order"
  namespace    = "urn:example:sales"
  description  = "Sales order header"
  xsd          = file("${path.module}/schemas/order.xsd")
}

# schemas/order.xsd:
#
# <xsd:schema xmlns:xsd="http://www.w3.org/2001/XMLSchema"
#             xmlns="urn:example:sales" targetNamespace="urn:example:sales">
#   <xsd:complexType name="Order">
#     <xsd:sequence>
#       <xsd:element name="OrderID" type="xsd:string"/>
#       <xsd:element name="Customer" type="xsd:string" minOccurs="0"/>
#     </xsd:sequence>
#   </xsd:complexType>
# </xsd:schema>
```

## Schema

### Required

- `data_type_id` (String) Technical ID of the data type. Changing it replaces the data type.
- `name` (String) Display name of the data type. SAP stores the schema's complex type under this name.
- `namespace` (String) XML namespace of the data type, for example "urn:example:orders". It must equal the targetNamespace of xsd. Changing it replaces the data type, because an in-place namespace change was not tested.
- `package_id` (String) ID of the integration package the data type belongs to. Changing it replaces the data type.
- `xsd` (String) The XML schema of the data type, for example file("${path.module}/order.xsd"): an xsd:schema with exactly one top-level complexType and the targetNamespace given in namespace. A change uploads the new schema in place.

### Optional

- `description` (String) Description of the data type. Omit it rather than setting an empty string.
- `save_as_version` (String) Version to save the uploaded data type under, for example "1.0.3", using SAP's SaveAsVersion function import. Without it, SAP keeps its own version number and uploads update the current draft. The content is saved as a new version only when this value changes, so bump it together with the content for each release; version then reports what SAP recorded.

### Read-Only

- `id` (String) Composite identifier in the form "<package_id>/<data_type_id>".
- `version` (String) The design-time version SAP reports for the data type.

## Import

```shell
terraform import sapintegrationsuite_data_type.order Sales/Order
```

The ID is `<package_id>/<data_type_id>`. SAP's normalized schema is not imported: after an
import, the first apply uploads the schema from the configuration.

## Limitations

- **SAP:** no documented request; the contract comes from the `$metadata` and tenant tests.
- **Complex types only.** The bundle of a simple type (`IsSimpleType`) was not examined.
- **No drift detection for the schema.** SAP renames the complex type and reformats the schema,
  so the provider does not compare SAP's schema with `xsd`. A change made in the UI is not shown
  as a diff.
- Message types and service interfaces that use the data type are not managed yet.
