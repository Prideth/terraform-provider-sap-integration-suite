# sapintegrationsuite_integration_adapter (Resource)

Imports a custom adapter, an `.esa` archive built with the SAP Adapter SDK, into an integration
package. This is not the way to use adapters from the Business Accelerator Hub, which are
imported from inside the integration flow editor, and it does not activate Integration Suite
capabilities. Cloud Foundry environment only.

**Status:** partial. SAP documents deploying and deleting adapters with example requests; the
create and read contract comes from the service's `$metadata` and the sibling artifact types.
There is no update: every change replaces the adapter.

## Prerequisites

- An integration package, usually [`sapintegrationsuite_integration_package`](integration_package.md).
- The adapter as an `.esa` file.
- An OAuth client with `WorkspacePackagesEdit`.

## Lifecycle

| Operation | What happens |
|---|---|
| Create | Uploads the `.esa` file into the package. SAP rejects an ID that already exists on the tenant. |
| Read | Reads name, version and the description SAP took from the file. |
| Update | None. |
| Replacement | Any change of `id`, `name`, `package_id`, `content` or `content_hash` deletes the adapter and imports it again. A deployment that references the unchanged `id` is not replaced with it and has no redeploy trigger; redeploy it with `terraform apply -replace` on the deployment resource. |
| Delete | Deletes the design-time artifact. |

## Example Usage

```terraform
resource "sapintegrationsuite_integration_package" "adapters" {
  id         = "CUSTOM_ADAPTERS"
  name       = "Custom Adapters"
  short_text = "Custom adapters"
}

resource "sapintegrationsuite_integration_adapter" "sftp_extension" {
  id         = "custom-sftp-extension"
  package_id = sapintegrationsuite_integration_package.adapters.id

  # SAP documents id as unique across the whole tenant, not just this
  # package, and rejects importing a duplicate id as an error - there is no
  # confirmed way to update an existing adapter's content or metadata in
  # place, so every attribute here forces replacement.
  name = "Custom SFTP Extension"

  content      = "${path.module}/adapters/custom-sftp-extension.esa"
  content_hash = filesha256("${path.module}/adapters/custom-sftp-extension.esa")
}
```

## Schema

### Required

- `id` (String) The integration adapter's technical ID. SAP documents this ID as unique across the entire tenant, not just the package, and states that importing an ID that already exists is rejected as an error — positive evidence that there is no update-in-place via re-import. Immutable: changing it replaces the resource. Import uses a composite "<package_id>/<id>" syntax despite id alone being SAP's confirmed key for Delete/Deploy — see package_id below for why.
- `name` (String) The adapter's display name. SAP's UI documentation states this is normally auto-filled from the imported *.esa file's own metadata; this provider still requires it explicitly so the configuration self-documents which adapter it expects to manage. No confirmed metadata-only update path exists (SAP's UI separately mentions editing "via View metadata", but no public API contract for it was found), so changing this replaces the resource.
- `package_id` (String) ID of the integration package this adapter belongs to at design time. Whether an existing adapter can be moved to a different package was not confirmed, so changing this replaces the resource rather than attempting an unverified move. Required at import time (as the first half of the composite import ID) because this project could not confirm that a plain GET by id reliably returns the owning package as a queryable property; leaving it unrecoverable would otherwise force a destructive replace on the very first plan after import, since this attribute is RequiresReplace.

### Optional

- `content` (String) Path to the local *.esa content file, for example "${path.module}/adapters/custom-sftp-extension.esa". Required to manage the adapter's content; left as-is on import until a matching configuration is applied, since SAP does not return a local file path for an existing design-time artifact. No public API for replacing an existing adapter's content in place was confirmed (see "id" above), so changing this replaces the resource.
- `content_hash` (String) SHA-256 hash of the content file, for example filesha256("${path.module}/adapters/custom-sftp-extension.esa"). Terraform replaces the adapter when this hash changes, for the same reason as "content".

### Read-Only

- `description` (String) The adapter description SAP stores, taken from the *.esa file on import. Read-only: the Integration Content API has no property this provider could set it through.
- `version` (String) The version SAP reports for the adapter, which SAP's UI documents as extracted from the *.esa file's own metadata rather than assigned by the API on each write.

## Import

```shell
terraform import sapintegrationsuite_integration_adapter.sftp_extension CUSTOM_ADAPTERS/custom-sftp-extension
```

The ID is `<package_id>/<id>`, although SAP identifies the adapter by `id` alone: the package
cannot be read back reliably, and without it the first plan would replace the adapter. The
[`sapintegrationsuite_integration_adapter`](../data-sources/integration_adapter.md) data source
returns the `package_id` to use. Setting `content` after an import replaces the adapter; leave
it out to adopt the adapter unchanged.

## Limitations

- **SAP:** importing an ID that exists is an error, so there is no update by re-import. The
  type and application shown in SAP's import dialog have no API property and cannot be set.
  The adapter ID is unique across the tenant, not only within the package.
- **Provider:** there is no data source that lists all adapters, because no list contract is
  documented. Files up to 32 MiB.
