# sapintegrationsuite_integration_flow (Resource)

Manages the design-time artifact of an integration flow: its model, scripts and resources,
uploaded as the ZIP file the Integration Suite UI produces when you download a flow. This
resource does not run anything. Deploying the flow is the job of
[`sapintegrationsuite_integration_flow_deployment`](integration_flow_deployment.md), because
SAP keeps design time and runtime apart: an upload changes the artifact, and the runtime keeps
the deployed version until it is redeployed.

**Status:** supported. Backed by `IntegrationDesigntimeArtifacts` of the Integration Content
API, including its documented `SaveAsVersion` function.

## Prerequisites

- An integration package, usually [`sapintegrationsuite_integration_package`](integration_package.md).
- The flow as a ZIP file on the machine that runs Terraform.
- An OAuth client with `WorkspacePackagesEdit`.

## Lifecycle

| Operation | What happens |
|---|---|
| Create | Uploads the ZIP into the package. If `save_as_version` is set, saves the content under that version. |
| Read | Reads name and version. SAP returns no file path or hash, so `content` and `content_hash` keep the values of the last apply. |
| Update | A new `content_hash` uploads the file again; a new `name` renames the flow. A changed `save_as_version` saves the uploaded content under that version. |
| Replacement | Changing `flow_id` or `package_id` creates a new flow. SAP identifies a flow by its ID within a package and has no operation to rename it or move it to another package. |
| Delete | Deletes the design-time artifact. A deployment resource that references this flow is destroyed, and so undeployed, before it. |

SAP writes the flow ID into `Bundle-SymbolicName` in `META-INF/MANIFEST.MF` when the flow is
created, and rejects every later upload with a different bundle ID. The provider therefore
uploads a copy whose bundle ID equals `flow_id` and shows a warning when it had to change it.
Your file and `content_hash` are not affected.

Uploading does not change the flow's version. A deployment that points at `version` therefore
does not redeploy on new content by itself: raise `save_as_version` together with the content,
or pass `content_hash` to the deployment's `redeploy_triggers`.

## Example Usage

```terraform
resource "sapintegrationsuite_integration_flow" "metering" {
  package_id = sapintegrationsuite_integration_package.utilities.id
  flow_id    = "metering"
  name       = "Metering"

  content      = "${path.module}/iflows/metering.zip"
  content_hash = filesha256("${path.module}/iflows/metering.zip")

  # Optional: save each release under an explicit version. Bump it together
  # with the content; a new version is saved only when this value changes.
  save_as_version = "1.0.3"
}
```

## Schema

### Required

- `flow_id` (String) The flow's technical ID. Immutable: changing it replaces the flow.
- `name` (String) The flow's display name.
- `package_id` (String) ID of the integration package this flow belongs to.

### Optional

- `content` (String) Path to the local ZIP file containing the integration flow project, for example "${path.module}/iflows/metering.zip". Required to manage the flow's content; left as-is on import until a matching configuration is applied, since SAP does not return a local file path for an existing design-time artifact. The copy that is uploaded carries flow_id as Bundle-SymbolicName in META-INF/MANIFEST.MF (the file itself is not changed, and a warning says when this happened): SAP rejects a content update whose bundle ID differs from the flow ID, so a ZIP exported under another ID could otherwise be created but never updated.
- `content_hash` (String) SHA-256 hash of the content file, for example filesha256("${path.module}/iflows/metering.zip"). Terraform only re-uploads the file when this hash changes.
- `save_as_version` (String) Version to save the uploaded integration flow under, for example "1.0.3", using SAP's SaveAsVersion function import. Without it, SAP keeps its own version number and uploads update the current draft. The content is saved as a new version only when this value changes, so bump it together with the content for each release; version then reports what SAP recorded.

### Read-Only

- `id` (String) Composite identifier in the form "<package_id>/<flow_id>".
- `version` (String) The design-time version SAP assigned to the most recent upload.

## Import

```shell
terraform import sapintegrationsuite_integration_flow.metering UTILITIES/metering
```

The ID is `<package_id>/<flow_id>`. Name and version are recovered; `content` and
`content_hash` are not, so the first apply after an import uploads the configured file once.
Make sure it is the content you want on the tenant.

## Limitations

- **SAP:** there is no operation to move a flow to another package or to rename its ID.
  Whether uploading new content keeps the values of externalized parameters is not
  documented; if it does not, the next plan of
  [`sapintegrationsuite_integration_flow_configuration`](integration_flow_configuration.md)
  shows them as drift and writes them again.
- **Provider:** files are read from local disk, up to 32 MiB; content is not fetched from Git
  or a URL. Drift in the flow's content made in the UI is not detected, because SAP returns
  no hash of it.
